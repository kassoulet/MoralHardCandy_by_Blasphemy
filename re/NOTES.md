# moral hard candy (Blasphemy, Summer Encounter 1999) - reverse-engineering notes (running log)

## Release / patch
- `MORAL.TXT`: original release text ("Any Pentium with Windows, DirectX 3+ ... `-lowmem` parameter exists", PII-350 recommended).
- `PATCH.TXT`: "new EXEs fix excessive memory usage, non-MMX bugs; overwrite the old bass.dll; **use candyw.exe if you can, the sound+timing is actually nicer**". So this folder is the *patched* release: CANDYD.EXE, CANDYW.EXE, BASS.DLL replaced; CANDY.DAT and 7KINGSI2.XM are the original data.
- `FILE_ID.DIZ`: "moral hard candy [kingsizebullmaster] at Summer Encounter 1999", Blasphemy feat/MD[tpolm].

## Executables
- `CANDYW.EXE` 382,512 B: PE32 (Windows GUI), Watcom C++ (sections AUTO/DGROUP, not packed), imports WINMM, USER32, DDRAW (DirectDrawCreate), KERNEL32 and **BASS.DLL** (BASS 0.6: BASS_MusicLoad/Play/PlayEx, ChannelSetSync/GetPosition, SlideVolume...: the XM is played by BASS and the demo is synchronised with BASS syncs/position). BASS.DLL itself is Petite-packed.
- `CANDYD.EXE` 306,333 B: MZ + **PMODE/W v1.33** (same stub/overlay layout as `../pls_amb`: PMW1 overlay at 0x2d00), Watcom C++ 32-bit flat, **MIDAS Sound System 0.6.2** for the XM (config menu: 12x Down + Enter = "No Sound" for the harness), VESA video (lfb), DOS timer ISR (PIT) as the demo clock.
- Both are builds of the same C++ source (same strings, same `candy.dat` loader, same "vicky's softrender engine (c) 1998-99 kaspar daugaard", libpng 1.0.2, a JPEG decoder, 3DS loader, s-buffer, zlib).
  Decision: **CANDYD.EXE is the canonical one for the reverse engineering** (unpackable and emulatable under Unicorn exactly like the earlier PMODE/W ports, no DirectDraw/BASS fakes needed); the Windows build is only different in the video/sound back-end (the patch text says its sound+timing is nicer, i.e. DOS timing = PIT ISR, Windows = BASS position).
- Command line (strings): `-audio` (manual sound setup), `-window`, `-lowmem` ("minimize memory requirements", "running in memory-saving mode"), `-hicolor` (hicolor instead of truecolor), `-triple`, `-double`, `-single` (page buffering). Stats at exit: "N frames rendered in X seconds (Y frames/sec)".

## Unpacking (done)
- `re/unpack_pmodew.py` (from pls_amb, + candy.dat stop) / `re/unpack_clean.py OUT.bin` run the stub's own loader under Unicorn and dump 64 MB RAM at the Watcom entry **0x554ec** (`jmp`, "WATCOM C/C++32 Run-Time system" string at 0x554ee). ~1 s. Also writes OUT.bin.json (GDTR/IDTR/ESP). Flat model like pls_amb: GDT at 0x1bf10, DS=0x860 (base 0), CS=0x868, ESP=0x125600.
- Layout: code+data object 1 at 0x1000..0x90000 (code to 0x56000, rodata/data after), object 2 at 0x100000.. (strings 0x101004.., BSS/heap). Program image `obj1.bin` = RAM[0x1000:0x90000] for `re/dis.sh START STOP`.
- **Pitfall found**: pls_amb's emucore put the DOS (DPMI 0100) buffer at 0x60000; here that is program *code* (the libpng filter code). It now lives at 0x90000 (free, below 0x100000 so real-mode segments still fit). Also `bytearray[a:b]=x` with a short slice shifted the whole VBE info block by 1 byte (mode list garbage) - lengths must be exact.
- PSP selector 0x24 at linear 0x600000 (free), mode list in emucore: VBE 0x100/0x101/0x4101 (8 bpp) plus 15/16/24/32 bpp 320x200..1024x768 (LFB at 0x30000000). The demo picks **VBE mode 0x4112 (640x480, truecolor)** with this mode list.

## CANDY.DAT (done, `re/extract_dat.py`)
"Blasphemy Library File": `[file data, every byte XOR 0x2a][directory: n x 21 bytes = name[13] (NUL padded), size u32, offset u32][dir_offset u32, count u32, magic 'OYZO' (= 'EPJ.' ^ 0x2a... magic stored as the XORed form)]`. Trailer = last 12 bytes. 85 files, 2,602,716 B: 59 PNG (RGBA textures, 512x256 mostly), 6 JPEG, 14 3DS scenes (te2rb, bikube2, ringe, boxpipe2, lysobj, flares, spiff1, 4xbold, volum, cigar, glowsph, boxphere, ... cameras + keyframes inside), infofont.png (font), plus a joke text ("they took our beer."). `7kingsi2.xm` is loaded from a separate file (2,185,859 B, 51 orders, 259.7 s by `re/xmtime.py`).
Names in the DAT are case-insensitive (INDUSTR1.JPG, YVER.PNG...). Extraction: `python3 -I re/extract_dat.py ../CANDY.DAT OUTDIR`.

## Engine (static findings)
- C++ framework with vtables: video manager (VBE LFB), screen manager, "vicky's softrender engine" (software rasteriser: render_wire/flat/gouraud/tex/tex_persp, s-buffer, z-buffer, 8bpp/32bpp textures, filters/blending), Scene3DS loader with keyframes (Position/Rotation/Scale/Camera roll keys), material manager.
- Main: `0x1d26f..` (arg parser from the option table at 0x101004), assets loaded: `candy.dat`, `7kingsi2.xm` (MIDAS), font `infofont.png`, then a list of **parts** at 0x10c790 (null-terminated pointer array, constructors show a progress bar "%02x/%02x"), main loop at **0x1dca7** (calls 0x1d800 = event processing, 0x1d790 = keyboard (ESC = exit, 's' = screenshot SCRnnnnn.TGA)).
- **Clock**: 0x2c230 = `ms = 1000 * tick / (1193181 / divisor)` where tick = `[0x112a60]` is incremented by the PIT ISR 0x2bf00 (installed by 0x2c0a0 with divisor `[0x112a68]`); the demo is therefore a function of PIT time, not of the music position (DOS version). The music just starts at the beginning (7kingsi2.xm). Time in seconds as double at `[0x10c7e8]` (= ms*0.001).

## Emulation state
- `emucore.py` (adapted from pls_amb): MHC_MEM env = unpacked image (default scratchpad/mhc/mem_clean.bin), runs from 0x554ec. Reaches the video mode set (0x4112), opens candy.dat and 7kingsi2.xm and spends a long time loading assets (libpng filter loops, ~12M guest insn/s under Unicorn).
- `re/snap.py OUT`: runs to the main loop 0x1dca7 once and saves a RAM snapshot (`OUT.mem` zlib, 96 MB) + CPU/DOS state (`OUT.st`) so the harness restarts instantly.

## Part table and harness (findings)
- Parts: 14 objects at ptr array 0x10c790 (-> 0x4000590.. step 0x20): `[0]` object (vtable at obj+4: +0x8 init? +0x10 start, +0x14 end, +0x18 render(double t), +0x1c event(ms*0.001, pos)), `[1]` start pos, `[2]` end pos, byte `[0xc]` started, `[0xd]` done, double `[0x10]` start time. Positions are MIDAS music positions `order<<8|row`: 0, 0x409, 0xb00, 0xf00, 0x1202, 0x1600, 0x1800, 0x1d00, 0x1e00, 0x2010, 0x2400, 0x2500, 0x2910, 0x2c00, end 0x3200. So **the parts are switched by music position events, not by PIT time** (ring buffer 0x10c8ac of {pos, ms}, write idx 0x10d0ac, read idx 0x10d0b0, fed by callback 0x1d630 from `0x2c1b0` = current music position, consumed by 0x1d800). In "No Sound" no events arrive and the part never starts: harness.py injects the rows of `xmtime.py` into the ring, runs 0x1d800 (sentinel return at 0x1dcb1), sets tick [0x112a60]=500 s so all events are due.
- Per frame: 0x1d400 spins on [0x10c7f8] (bumped by ISR 0x1d690): the harness hooks 0x1d490 and bumps it. Pause flag [0x10c7f0]!=0 -> demo time [0x10c7e8] is whatever we write.
- VBE 0x4112 is **24 bpp packed** (pitch 1920), not 32. Texture/buffer conversion routine at 0x83bb4 (32 -> 24 bpp, 4 px per iteration).
- **Black LFB solved**: the demo renders into a 32 bpp 512x256 surface (object: w,h,pitch,buf at +0,+4,+8,+0x10; e.g. buf 0x402ffb8 pitch 0x800) and 0x54d33 converts it line by line (indirect call [obj+8], converters at 0x83ae9/0x83b17/0x83bb4) into the 24 bpp LFB. Our half-faked video manager hands that blit a bogus destination (LFB+0x130, pitch 1), so the LFB stays empty. harness.py hooks 0x54d51 to remember the source surface and dumps it (letterboxed into 640x480). 3.8 M guest insns per frame (hot code 0x82e40..0x83c20, MMX blit/alpha).
- Golden run: `python3 harness.py boot 0 259.6 0.2 OUT` -> 1274 frames (0-254.6 s, ~0.5 s host per frame, ~17 min), then it crashes (read of unmapped) at the demo end, expected. `tools/mkgold.py` crops to 512x256 webp.
- Not a pure function of t: t=70 alone != t=70 after stepping through 69.96 (deterministic though: identical on repeat). Frame-to-frame state exists.
- Parts -> files: `re/partmap.py` (string refs inside each part's functions; part 4 (ring) uses the base-class code that holds y-files/ringe). Part 1 = title (logo2.png fade, fitted in web/part0.js).
- Alpha blend MMX at 0x82e7b (two px/iter, premultiplied, alpha byte = transmittance by inference), 32->24 packer 0x83bb4, solid fill with software prefetch 0x83a80: described in WRITEUP-asm.md.

## Phase 4: te2rb line pass located (probe_lines.py)
`probe_lines.py SNAP T0 T1 STEP OUTDIR` (env LNOUT=prefix): harness + hooks on 0x31030 (sprites) and **0x2ff80 = the wire-line inner loop**; pickles the per-frame call list (eax=dst addr, ebx=count-1, edx=fraction accumulator, globals 0x113310 table, 0x113314/0x113318 major/minor pixel step, 0x11331c slope) to LNOUT_<t>.pkl. Run from the snapshot dir, ~1 s host per frame.
- 0x2ff80 is an anti-aliased, saturating ADDITIVE line: per step it writes 2 pixels ([edi] and [edi+minor step]) with complementary weights cl / ~cl taken from the colour ramp built by 0x2fe70 (1024 dwords at [0x113310], args = 3 floats = per-channel gain; set as line fn at [0x1078d0] by 0x29e74). Saturation: the and 0xfefeff / and 0x1010100 / shr 7 trick. A twin at 0x30010 is the subtractive version.
- ~2000 calls per frame (t=27.2..27.8: 2014, 2007, 2001, 1981), mostly 1-2 px long (max ~234): the wire object is a dense mesh (Tube03), clipped/set up in 0x300a0.. (flag bits for out-of-range, per-line DDA).
- Frame structure of 0x29da0: camera matrices (0x36480, 0x36810, 0x3b090, 0x3b170, 0x315f0), line colour ramp (0x2fe70), scene render with the line fn (0x36250), background sprite blit, then either the "fade-in/flash" branch (the 256-entry sin/cos sum palette, 0x2a04f loop -> 0x43370 surfaces -> 0x2fdb0 compose, scan bars) or the plain branch (0x43990 filter at opacity 0.67/0.17, 0x30e30 blit).
- Still to do for a JS port: decode 0x36250 (mesh walk, transform, projection, clip 0x300a0) and the matrix helpers; the sprite layers and scan-bar compose (0x2fdb0) after that. Estimated large (several sessions); golden frames remain the source for 26.5-56 s.

### 0x36250 decoded (structure only) - probe_calls.py
`probe_calls.py` = probe_lines.py + counters on the virtual calls and on the caller of 0x2ff80. NB: it must be stepped from t<=26.2 (a probe started directly at 27.6 from boot.mem runs part 1).
- **0x36250(eax=render ctx, edx=target surface, stack: 4x4 view matrix + float t)**: sets the viewport from the surface (w/2, h/2 as floats at ctx+0xc..0x18), builds projection (0x3af80, aspect from ctx+0x24/0x28) and view (0x3aa50) matrices into ctx+0x58/+0x98, then **0x36490** (scene walk), then for ctx+0x1c in {1,2,3} **0x365d0**, then target vtable+0x10 (flush), then frees three lists (0x31520).
- **0x36490**: two intrusive lists. List A (ctx+0x3c -> ...): per object with byte [obj+0x10]!=0 calls vtable `[obj+0x268]+4` (mesh transform/queue; observed vtable 0x106f74, 3 calls/frame = 3 mesh objects). List B (ctx+0x40): calls `[obj+4]` vtable[0] (lights/other). ctx+0x38 = 1/ctx+0x34.
- **0x365d0**: 4096 depth buckets at ctx+0x20 (array of list heads); each queued face is drawn by its own vtable[0] and the bucket emptied. Back-to-front order is irrelevant for the additive line pass (clamped sum is order independent), but matters for any filled mode.
- Queued face objects (observed ~670 per frame, `eax` at 0x365e8): +0 = vtable fn **0x40660**, +0xc = vertex count (3), +0x10 -> vertex pointer array (screen vertices: x at +0x18, y at +0x1c, others +0x44/+0x50 = attributes), +0x14..0x1c = face normal (float3), +0x30 = wire flag. 
- **0x40660** = face renderer: backface test from the 2D cross product of the first vertices (0x40734..0x40763), polygon edge walker, and for wire faces the edge lines go through **0x300a0 (line setup with clip flags, DDA) -> `call [0x1078d0]` at 0x308f0 = 0x2ff80**. All 2014 calls/frame come from return address 0x308f6.
- So the missing pieces for a port: (1) the mesh object's method behind [obj+0x268]+4 (world->view->screen transform of the 3DS vertices, face queueing, per-face colour/depth), (2) the 3DS keyframe player feeding the model matrices (0x36480/0x36810), (3) 0x300a0 clipping + DDA (read, not yet ported), (4) the 0x2fdb0 compose. Next: disassemble 0x31af0 (vtable entry of the mesh class at 0x106f74) and find where vertices are projected.

### Mesh pipeline (vtable 0x106f74, method +4 = **0x32640**, found by watching writes to the projected vertex fields)
Stages called in order by 0x32640 (mesh object eax; ctx at [obj+0x48], source model at [obj+0x44]): 0x32390, 0x327d0, 0x32840, 0x32db0, 0x33a40, 0x33f70, 0x34010, (0x340a0 if model mode 1/2), 0x34110 (queues faces into the depth buckets via ctx vtable+0xd8, key = face depth at face+0x34).
- Vertex struct (linked by [v+0x5c]): +0x0..: model xyz; camera-space xyz written at +0xc/+0x10/+0x14 (by 0x31690 = 4x3 transform: `out.x = x*m[0]+y*m[4]+z*m[8]+m[0xc]`... see disasm, matrix stored with rows at +0,+4,+8 / +0x10.. / +0x20.. and translation at +0x30..0x38), **screen xy at +0x18/+0x1c written by 0x33f70** (perspective: invz = 1/v.z; sx = cx + v.x*invz*kx; sy = cy - v.y*invz*ky; centre/scale from ctx+0xc..0x18 = surface w/2, h/2 based), **1/z at +0x50 and scaled uv-ish pair at +0x40/+0x44 written by 0x34010**, face depth key by 0x340a0 = (z0+z1+z2)*const [0x102c3f].
- Writes observed per vertex per frame (EIP): 0x316ae/316cc/316eb (transform helper), 0x327ea/327ef (0x327d0), 0x32e00 (0x32db0), 0x33c7a/33c8b (0x33a40), 0x33fef/33ff0 (projection), 0x3403d, 0x34068/34069 (0x34010).
- Port plan: 3DS vertices + keyframe matrices (m3ds.py parses the chunks; the 35*(t-start) timing is known) -> 0x31690 transform -> projection -> backface (cross product in 0x40660) -> 0x300a0 clip + DDA -> 0x2ff80 additive AA pixels with the 0x2fe70 ramp. Float32 stores (fstp dword) must be mirrored with Math.fround; intermediates are x87 extended.
- Not yet read: 0x32390/0x327d0/0x32840/0x32db0/0x33a40 (per-object matrix setup, lighting/normals?, clipping against the near plane?), and 0x300a0 line clip.

### 3DS -> engine vertex mapping (Tube03) found
Engine model coords (vertex +0..+8) = `(t.y - V.y, V.z, V.x - t.x)` where V = raw 3DS vertex, t = the object's 0x4160 local-matrix translation (865.025, 113.970, 0): the rotation part of 0x4160 is applied inverse (object space) and then the axes are swapped y<->z (right-handed 3DS -> left-handed engine). Checked on frame t=27.8 (probe_faces.py dump): 2567 engine vertices within |x|<1000 match the file vertices to 7.6e-6 (float32 rounding; the ~1% outliers are the small second mesh). The engine stores 723 unique positions (face-split duplicates) vs 844 unique in the file, 1093/1704 faces drawn. Next: camera 4x3 from Camera02 pos/target/roll keys (fit_te2rb.py has `view()`), compare to the fitted per-mesh M at +0xc.

### te2rb camera decoded (re/te2rb_cam.py) - verified vs engine camera-space vertices, max err 2e-4 (float32) at t=27.0/27.8/28.0
- frame f = 35*(t-26.7) (part start 26.7, not 26.5). Camera02 pos / target / roll tracks use **Catmull-Rom** (TCB=0; tangents scaled 2*d1/(d0+d1)); fits the engine camera position to 0.000 at f=10.5,17.5,...,45.5.
- Camera-space = (P - pos) . R . diag(0.25, 0.5, 1): R's columns are the camera axes (z = normalize(target-pos), x/y = unrolled right/up rotated by -(roll mod 360) deg), then the x/y scales 1/4, 1/2 are baked in (so the projection stays `255.5+256*x/z`, `127.5-128*y/z`; FOV key 122.63 is not used directly).

### te2rb wire pass: selection + line setup (re/te2rb_line.py, verified on engine dumps)

- 0x300a0 (no-clip path) modelled in `setup()`: x/y negated and step -4/-pitch when dx/dy <= 0; major axis = larger |d|; slope = float32(minor/major)*2^32 (clamped 0xFFFFFFFF) = [0x11331c]; start pixel = trunc(x0), count = trunc(x1)-trunc(x0), minor position v = float32((xi-x0)*slope+y0), minor int = trunc(v) (minus 1 if negative), start skipped while |minor|<1 or |minor|>dim-2 (the 1 px border), frac = (v-minor)*2^32 low dword, addr = base + minor*minorstep + xi*majorstep. ## te2rb float32 camera decode (verified bit-exact)
- The program runs with x87 precision control = 24 bits: every + - * / sqrt is rounded to float32 (order of stack ops matters). fpatan/fsin are not rounded; pi/2 tbyte = 0xc90fdaa22168c000/2^63.
- Part start is 26.5; engine frame f = f32(f32(t-26.5)*35). probe_faces/probe_lines dumps are labelled with the NEXT step time (dump at loop head): file labelled T = frame T-0.2 (calls(T-0.2)).
- Key struct stride 0x98: +0 frame, +8 value, +0x18 in-tangent, +0x28 out-tangent. Hermite in float32 per op: u=(f-K0)/(K1-K0); A=u*u; B=A*u; h2=-2B+3A; h1=(2B-3A)+1; h3=(B-2A)+u; h4=B-A; value=((h2*P1+h1*P0)+h3*T0)+h4*T1.
- View = ((T(-pos)*Ry(yaw))*Rx(pitch))*Rz(roll); matmul out[i][j]=((p0+p1)+p2)+p3. ctx+0x98 = view*diag(.25,.5,1). Tube03 world W rows [0,0,-1],[0,1,0],[1,0,0], translation (865.025146484375,0,113.96991729736328). obj+0x110 = W*V, obj+0x150 = W*(V*P). Vertex 0x31690: cam=((x*M0+y*M4)+z*M8)+M12; projection 0x33f70: sx=(256x)*iz+255.5, sy=127.5-(128y)*iz, iz=f32(1/z).
- Code: te2rb_f32.py (model), te2rb_f32test.py (asserts matrices + all ~2500 vertices cam/screen bit-exact at t=27.0..28.0 vs golden/cam, golden/pf2), te2rb_wire.py (predicted line calls exact: no extras, 1952..1990 of 1981..2014 captured), probe_cam.py (capture).
- Key arrays are loaded from golden/cam/c_cam.pkl (engine dump); tangents not yet derived from the 3DS.
